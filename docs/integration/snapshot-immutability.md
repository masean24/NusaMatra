**3. Why `pendidikan_daerah_3t` changed from `rankable: false` (45 %) to `rankable: true` (100 %).**

The preset weights are identical in both responses (`edu_damaged_classrooms_pct 3000`,
`edu_mean_years_schooling 2500`, `edu_student_teacher_ratio_sd 2500`, `inf_internet_household_pct 2000`).
What changed is availability. Two of its four indicators had no data at 15:18Z (45 % of the weight
available, effective weights 5556/4444). They were ingested at 16:36 from `kemendikdasmen_statistik_2026`,
so all four are now available (100 %, effective weights equal the requested weights). The `rankable` flip
is therefore **consistent with the server's own availability rule**. It is not a contract change. The
defect is that it happened under an unchanged snapshot id.

Consequences visible in `POST composite-query` (national, education weights):
- 513 of 514 composite scores changed.
- Example: Lanny Jaya 9507 went from 91.65 rank 5 to 79.62 rank 3.
- `inf_internet_household_pct` is still `IMPUTED_PROVINCE` in all 514 rows.

**4. Open contract inconsistency (not fixed in the frontend).**

`composite-query` returned a full ranking at 15:18Z for weights whose preset was `rankable: false`. The
frontend blocks the ranking presentation from the `availability.rankable` of the presets response it loaded.
It never alters the scores.

## Frontend consequences (implemented)

- A Paspor Bukti can **not** claim reproducibility. `snapshot_id` is shown as the id the server reported,
  with the disclosure that the same id has been re-published with different content.
- Exports state `pinnedInputs: false`. They keep the values, metadata and timestamps exactly as received,
  plus the browser receive time.
- No report id, content hash or server timestamp is generated by the frontend.
- `manifest_checksum` is labelled as not being a content digest.
- Live end-to-end tests assert invariants (ranking only after the checks pass; non-rankable preset never
  ranked), not data-dependent values. Mocked tests assert the captured 15:17Z state and say so.

## Backend requirements

1. **Immutable snapshots.** Any change to observations, datasets, availability, presets or coverage creates
   a new `snapshot_id`. A published snapshot is never re-published in place; `created_at` is never
   overwritten.
2. **Content digest.** `manifest_checksum` (or a new `content_digest`) is computed from the canonical
   content of the snapshot (observations, catalog, presets, dataset hashes) and changes whenever the
   content changes. Document the algorithm and the canonicalisation.
3. **Pinning.** All read endpoints and `composite-query` accept a snapshot parameter (e.g.
   `?snapshot=<id>`) and answer from exactly that snapshot, or with an explicit error if it was retired.
   Responses echo the snapshot id and digest they were computed from.
4. **Server-issued evidence (if Paspor Bukti should become an archive).** An endpoint that stores the
   query, the pinned snapshot and the result, and returns a server report id and a server timestamp. Until
   then the passport stays browser-assembled.
5. **Consistent metadata.**
   - `indicator_completeness_pct` must agree with `/indicators/coverage`.
   - `notes` must not claim "100% verified" while `IMPUTED_PROVINCE` values are served.
   - Timestamps must carry a time zone.
6. **Contract.** `composite-query` returns either no ranking or an explicit non-rankable status for weight
   sets that do not meet the same availability rule that sets `rankable: false` on presets.
